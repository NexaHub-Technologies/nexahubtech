# How We Teach — NexaHubTech

> The pedagogy behind every NexaHubTech course: the mental model before the syntax, one idea at a time, and a session built in three parts.

Canonical page: https://www.nexahubtech.company/teaching

## Principles

01. **The model before the syntax** — Syntax is the cheapest part of programming and the first thing you forget. We spend the time on the idea underneath — what the machine is actually doing — because that is what survives, and what lets you pick up a language nobody taught you.
02. **One idea at a time** — Chunk-based teaching: a session introduces a single concept, uses it, and stops. Four ideas in an hour feels productive and teaches none of them, because there is no room left to be usefully confused about any one of them.
03. **Being stuck is the lesson** — Exercises are pitched just past what you already know, which means you will get stuck. That is the part where the learning happens, so sessions leave room to be wrong out loud before the answer turns up.
04. **You should be able to explain it** — Code runs by accident all the time, so the test of understanding is never that it works. It is whether you can say why it works. Every module ends with something you could defend to another person.

## Every session, in three parts

01. **A mental model** — The session opens with the idea in plain language, before a line of code appears — usually as a picture of what the machine is doing, or an analogy that holds up under pressure. *Why:* Syntax attached to an idea is memorable. Syntax attached to nothing is a list.
02. **An exercise brief** — A focused task you cannot finish by pattern-matching the example. It forces you to use the concept, which is how you find out whether you actually hold it. *Why:* Reading code you understand feels identical to reading code you don't.
03. **A model answer** — A worked solution written the way we would write it, with the reasoning left in. It is there to compare against yours, not to replace the attempt. *Why:* Nobody learns what good looks like from a blank page and a passing test.

## What we deliberately do not do

- **Slides, read aloud** — If a session could have been a document, it should have been a document. Time together is for working through the hard part, not narrating bullet points at you.
- **Copy-along tutorials** — Typing what somebody else typed produces a working app and no transferable skill. You will build things here that you have to think your way through.
- **Twelve tools in six weeks** — A tour of frameworks looks impressive on a syllabus and leaves you unable to use any of them. We go slower, over fewer things, deliberately.
- **Frameworks before foundations** — React before JavaScript, or a CSS framework before layout, produces developers who are fluent right up until something breaks. The course order is not an accident.
